# D-Fire 데이터·학습·평가·후처리 기술 기록

## 무엇을 학습했고 무엇을 하지 않았나

주력 모델은 공식 사전학습 `yolo11n.pt`를 불꽃·연기 두 클래스에 전이학습한 모델이다. Colab T4로 70epoch를 완료했다. YOLO26n은 그 전에 3epoch 시험했고 별도 보관했다. 두 모델을 결합하거나 동일 조건으로 최종 우열 비교하지 않았다.

현재 서비스 모델 SHA-256은 `57c133a489976dc2f7341381b12cf160622e0bbaff33aeffdee4926e2093611d`이다. 10-05 이후 주요 탐지 개선은 후처리/시간·공간 게이트이며 새 데이터로 재학습한 결과가 아니다. hard-negative 보강, ONNX 최적화, 실제 CCTV 사건 평가, 새로운 카메라 도메인 적응은 아직 미완료다.

## 데이터 위치와 의미

Drive의 `Data/DFire/D-Fire.zip`에는 이미지와 YOLO 라벨이 함께 있다. `d-fire 텍스트 분할.zip`은 이미지 파일명 목록이며 라벨 박스 파일이 아니다. 실제 클래스 매핑은 **0=smoke, 1=fire**다. 초기 통합가이드 PDF의 예시 YAML에는 반대 매핑이 있어 그대로 복사하면 안 된다. 현재 검사·모델·서비스는 실제 D-Fire 순서를 사용한다.

YOLO 라벨 한 행은 `class x_center y_center width height`, 좌표는 이미지 크기로 정규화한다. 빈 TXT는 fire/smoke 박스가 없는 배경 이미지이며 필요한 음성 예다. 파일 개수 일치만으로 라벨 의미가 정확하다는 보장은 없다.

| 구분 | 이미지 수 | 용도 |
| --- | ---: | --- |
| 원본 train | 17,221 | fold로 train/val 분할 |
| 현재 train | 13,776 | 가중치 업데이트 |
| validation | 3,445 | 학습 중 평가·모델/규칙 선택 |
| 원본/최종 test | 4,306 | 최종 선정 후 평가 |
| 전체 | 21,527 | 라벨 파일 수도 동일 |

현재 공식 fold 1의 파일명 교차/누락은 0이다. 초기 출력에서 fold 2~5 등의 validation 3,444가 보였지만 실제 선택 fold 1은 3,445다. 기존 설계의 camera/event 그룹 분할, pHash 유사 장면 누수 검사까지 완료한 것은 아니다. 새 CCTV 평가 자료는 사건·카메라·날짜별 그룹 분할을 해야 한다.

## 라벨 정리 v2

사전 검사에서 340개 라벨 파일·397행이 변경 대상이었다. 18행의 0면적 박스를 제외하고 379행의 이미지 경계 밖 좌표를 클리핑했다. 원본 ZIP은 수정하지 않고 추출한 학습 사본에 적용했다. 원래 행·정리 행·사유를 `label_corrections.json`에 기록했다.

정규화 중심/너비/높이 각 값만 확인하면 박스 모서리의 경계 이탈을 놓친다. 네 모서리까지 검사하는 이유다. 잘못된 클래스·NaN·음수 크기를 임의 추정하지 않고 중단한다. 세 분할에 동일 사전 규칙을 적용했으며 정리 전 결과와 완전히 같은 데이터셋이라고 보고하지 않는다.

일부 JPEG의 끝부분 복구는 `/content` 또는 CPU 검증용 추출 사본에서만 수행했다. 원본 ZIP 불변과 모든 실험 때 원본 전체 ZIP SHA를 새로 검사했다는 주장은 다르다. 후처리 비교는 CRC/기존 manifest/라벨 SHA를 대조했고 원본 전체 SHA를 매번 끝까지 새로 계산한 것은 아니다.

## 환경과 학습 설정

- 로컬: Python 3.12.10, CPU PyTorch, 별도 `.venv`; 학습은 하지 않고 코드/검사/추론을 수행한다.
- 초기 Colab 확인: Python 3.13.15, T4 약 15GB, torch 2.11.0+cu128. 후속 로그에는 cu130이 보인다. 실제 실행별 환경을 따로 보존한다.
- 본 학습: YOLO11n, Ultralytics 8.4.143, 640px, batch 16, 최대 80epoch, patience 15, seed 42, deterministic true, workers 2, device 0, AMP true, optimizer auto, cache false.
- 두 팀원은 각자 노트북 사본/런타임/실행 ID를 사용한다. 독립 실행이 자동 병렬 분산 학습이나 가중치 합산을 의미하지 않는다. 같은 seed도 GPU·라이브러리 차이로 완전한 동일성을 보장하지 않는다.

## 3epoch 시험과 본 학습을 혼동하지 않기

YOLO26n 3epoch 당시 전체 precision 약 0.6683, recall 0.6068, mAP50 0.6621, mAP50-95 0.3614였다. 학습량 3/80=3.75%는 설정된 epoch 비율이지 성능 완성도 3.75%가 아니다. 100장 overfit은 가이드의 제안이며 실제 전체 fold 3epoch 시험과 동일한 작업이라고 쓰지 않는다.

## 중단과 70epoch 재개

최초 실행은 `jongwon_20260930T144603Z_51fb455c`다. 69epoch 완료 백업을 검증한 후 70epoch 도중 중단됐다. 사용자 선택으로 80을 채우지 않고 `jongwon_to70_20261004T144737Z_9154ce3d`에서 70까지 마무리했다.

이번 기술 아카이브 점검에서 확인한 증거:

- `latest_checkpoint.json`: directory `checkpoints/epoch_0070`, epoch 70.
- `final/results.csv`: epoch 70 행 존재. 70행의 validation mAP50 약 0.77210, mAP50-95 약 0.45175.
- `status.json`: state `validated`, model `final/best.pt`.
- 최종 best 평가 결과 SHA는 현재 서비스 모델과 동일하다. 체크포인트 저장본과 최종 최적화 저장본의 SHA는 별도로 기록한다.

best.pt는 70번째 업데이트 후 last.pt와 같은 의미가 아니다. 검증 성능이 가장 좋았던 epoch 가중치가 선택된다. 재개 전 학습 로그의 누적 time과 재개 70행의 time은 세션이 달라 총벽시계 시간으로 단순 합산하지 않는다.

## 모델 교체 계약

새 best.pt를 교체할 때 모델 이름만 바꾸지 않는다. 신뢰된 파일의 클래스 순서·입력/출력 형식·SHA, 해당 모델용 정책의 SHA/해상도/threshold, 실제 회귀 예제, 준비 상태와 알람 버전을 함께 갱신한다. pt는 임의 코드 실행 위험이 있는 형식이므로 외부 불명 파일을 로드하지 않는다.

서비스는 `models/best.pt`와 `models/fire_policy_v1.json`을 사용하고 모델은 시작 때 한 번 로드한다. 파일 교체만으로 개선을 보장하지 않는다. 체크 후 서버를 재시작하고 기존 버전으로 되돌릴 수 있어야 한다. 모델 파일은 현재 공개 저장소에 포함하지 않는다.

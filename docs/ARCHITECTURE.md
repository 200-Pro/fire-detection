# 아키텍처와 범위

## 현재 구현: 제한된 카메라 수를 위한 모듈형 단일 서비스

```text
휴대폰/PC 브라우저                   로컬 RTSP edge 어댑터
 getUserMedia → JPEG                    OpenCV → JPEG
           └──── 카메라별 Bearer 키 ───────────┘
                              ↓
              FastAPI 프레임 입력 (인증·크기·속도 검사)
                              ↓
              bounded admission → 단일 YOLO 실행기
                              ↓
              모델별 후처리 → 카메라별 시간 확인 게이트
                              ↓
              알람 DB 기록 + 증거 저장 + WebSocket
                              ↓
              React 관제 화면 / 담당자 확인·처리

          SQLite(local) / PostgreSQL(deployment)
          local evidence volume / S3 (설정으로 전환)
```

초기 카메라 수·CPU 서버에 불필요한 서비스 분산을 늘리지 않고, 추론·알람·보안·스토리지를 모듈로 분리했습니다. 사용자 화면은 모델 파일과 직접 결합하지 않습니다. 모델은 시작 시 한 번 로드되며 API 요청마다 로드하지 않습니다.

## 확정한 프로토타입 기능

실시간 영상 전체를 중계하는 플레이어가 아니라 **약 1초 간격 이미지 기반 감지/프리뷰**입니다. fire가 최근 5프레임 중 3회 있고 최초/최근 양성 간격이 최소 1초이면 불꽃 후보 알람을 만듭니다. clear 5프레임으로 지속 신호 latch를 해제하고, 재알림 최소 간격은 30초입니다. 신호 간격이 4초보다 크면 프레임 이력을 초기화합니다. 12초간 수신이 없으면 오프라인 표시입니다.

이 시간 확인 기준은 시연용 휴리스틱입니다. 실제 사건 recall·탐지 지연·시간당 잘못된 경보를 측정하지 않았으므로 현장 기준이라고 주장하지 않습니다. smoke는 화면 후보로 표시하지만 이번 알람 발생 조건은 fire입니다.

## 데이터 경계

- 웹 관리자 세션: 서버 DB에 해시로 저장한 랜덤 토큰, HttpOnly 쿠키. 로그아웃 시 폐기.
- 카메라 연결 코드: 8자리 랜덤 문자열, 10분 유효, 사용 후 제거. 조건부 SQL UPDATE로 동시 요청 중 한 건만 원자적으로 교환합니다. 등록/재발급은 관리자만 가능.
- 카메라 전송 키: 랜덤 토큰의 해시만 DB 저장, 24시간 유효, 한 카메라 전송에 한정. 중지 시 폐기.
- 증거 접근: 관리자 소유권 검사 후 전달. 이미지 디렉터리를 공개 정적 파일로 열지 않습니다.
- 프레임: 2MB 이하, 최대 16M pixels·최대 변 4096, JPEG/PNG/WebP. 최근 이미지 메모리 캐시와 알람 증거만 저장.
- 외부 CCTV: 서버의 임의 URL fetch를 열지 않고 현장 edge 어댑터가 카메라별 인증으로 전송.
- 모델: 운영자가 제공한 신뢰된 `.pt`만 사용. 모델 업로드 UI 없음. PyTorch 파일은 임의 외부 파일을 실행하지 마세요.

## AWS 확장 제안: 아직 배포하지 않음

HTTPS ALB → Nginx/React + FastAPI ECS 서비스, RDS PostgreSQL, private S3 evidence, Secrets Manager, CloudWatch. 데이터베이스는 private subnet, DB/S3 접근은 task role·최소 권한으로 제한합니다. 정적 화면은 이후 S3/CloudFront로 분리할 수 있습니다. CPU 추론의 카메라 수·배치·해상도 처리량부터 측정한 뒤 GPU/EC2 또는 별도 추론 worker를 선택합니다.

현재 코드가 허용하는 배포는 API **한 인스턴스, Uvicorn 한 worker**입니다. 카메라 상한 8은 메모리/입력 제한이며 8대의 처리량 보장 수치가 아닙니다. 게이트·팬아웃·프리뷰·속도 제한은 메모리이므로 서버 재시작 때 초기화됩니다. 종료되지 않은 기존 알람 기록은 DB에 남습니다.

다중 인스턴스 단계에는 camera routing/Redis pubsub 또는 broker, shared rate limiting, 분산 알람 deduplication, durable temporal state, idempotent frame/event keys, 추론 작업 취소/재시도 정책이 필요합니다. 무작정 replica/worker만 늘리면 중복 알람과 상태 불일치가 발생할 수 있습니다.

## 실서비스 공개 전 체크리스트

- 실제 카메라별 주야간/역광/안개/구름/조명 hard-negative와 산불 조건 검증.
- 프레임 박스 평가와 사건 단위 recall·시간당 경보·탐지 지연을 구분해 측정.
- 부하 테스트, 장시간 soak test, 회선 끊김/모델 실패/DB 실패/증거 저장 실패 훈련.
- 역할별 권한/조직 분리/계정 복구/비밀번호 재설정/공유 브루트포스 대응. 현재는 단일 관리자 워크스페이스이며 현재 비밀번호 확인 기반 변경과 다른 세션 폐기는 구현·테스트했습니다.
- 재시작/다중 작업자 시 게이트 내구성 추가 점검. 현재 동시 코드 교환과 추론 중 연결 해제는 자동 테스트했습니다.
- TLS, WAF/공유 rate limit, DB 백업·복구, 비밀 관리, 이미지 보존/삭제 정책.
- 증거 S3 최소 권한·암호화·보존 정책, 실패 시 운영 알림.
- 외부 공개에 대한 Ultralytics 모델/코드 및 D-Fire 권리 검토.

즉, **배포 가능한 방향의 기본 구조를 구현한 프로토타입**이지 인증된 화재 안전 제품이나 고가용성 관제 시스템이 아닙니다.
